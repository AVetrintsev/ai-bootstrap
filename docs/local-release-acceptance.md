# Приёмка локального релиза

Приёмка выполняется на отдельной Ubuntu Server 26.04 LTS `amd64`.
Все команды проверки запускаются на этой Linux VM. Рабочая VM владельца
не заменяет проверку первого запуска на чистой системе.

## Подготовка

1. Установить Ubuntu Server, проверить SSH по ключу, `sudo`, `systemd-resolved`
   и `/dev/net/tun`. Сохранить чистую контрольную точку до установки платформы.
2. Зафиксировать полный SHA релиза. Подготовить рабочий YAML с правами `0600`
   вне Git и выбрать `portal.transport: local-http`.
3. Установить релиз по README. Если исходники переданы через `git archive`,
   отдельно указать это в протоколе: такой запуск проверяет `install.sh`,
   но не получение приватного релиза обёрткой `bootstrap.sh`.
4. Сохранить вывод установки без ссылки активации и секретов. Проверить
   статусы критических служб и `SKIP` для публичного DNS, ACME и Globalping.
5. Открыть портал через SSH-туннель, активировать владельца и проверить пустой
   список проектов. Ссылку активации, TOTP, cookie и рабочий YAML в протокол
   и репозиторий не записывать.

Для автоматической установки Ubuntu параметр `apt.fallback` принимает
`offline-install`, `abort` либо `continue-anyway`. Значение `offline`
не принимается Subiquity. Проверять конфигурацию следует схемой версии,
которая находится на выбранном ISO, а не только общим YAML-парсером.

На отдельной VM приёмки жизненный цикл владельца проверяется через настоящий
портал. Сценарий **сбрасывает владельца**; запускать его до остальных браузерных
проверок. Он сохраняет новые тестовые cookie и TOTP только в закрытом `STATE_DIR`.
Истечение суток, месяца и окна ошибок моделируется изменением сроков в тестовой
базе, без изменения часов VM. Решения о доступе принимает установленный портал.

```bash
python3 tests/accept_portal_lifecycle.py http://localhost:8080 /root/acceptance-owner --reset-owner
```

## Два проекта и агенты

Из портала один раз подключить GitHub App и добавить два разрешённых
приватных репозитория. Дождаться готовности индексов и подключения Canvas.
Записать идентификаторы проектов в переменные `PROJECT_A` и `PROJECT_B`.
Настроить доступ Qwen и отдельный вход Codex по подписке. Вызовы моделей
учитываются в существующих лимитах провайдера и проекта.

Существующие сценарии выполняются последовательно от root. `PYTHON` —
окружение проверок с Playwright, `CHROMIUM` — Linux Chromium. Перед запуском
проверить импорт Playwright в этом окружении.

```bash
bash tests/accept_github_projects.sh "$PROJECT_A" OWNER/REPO_A "$PROJECT_B" OWNER/REPO_B
bash tests/accept_resources.sh "$PROJECT_A" "$PROJECT_B"
python3 tests/accept_project_tools.py "$PROJECT_A"
python3 tests/accept_project_tools.py "$PROJECT_B"
for project in "$PROJECT_A" "$PROJECT_B"; do
    for agent in codex qwen; do
        python3 tests/accept_project_agents.py "$project" "$agent"
        "$PYTHON" tests/accept_canvas.py "$project" "$CHROMIUM" "$agent" project-tools
    done
done
python3 tests/accept_codex_isolation.py "$PROJECT_A"
"$PYTHON" tests/accept_canvas_revocation.py "$PROJECT_A" "$CHROMIUM"
python3 tests/accept_project_memory.py "$PROJECT_A" "$PROJECT_B"
"$PYTHON" tests/accept_shared_memory.py "$PROJECT_A" "$PROJECT_B" "$CHROMIUM" ./install.sh
"$PYTHON" tests/accept_shared_rules.py "$PROJECT_A" "$PROJECT_B" "$CHROMIUM" ./install.sh
```

Матрица должна содержать завершённые вызовы инструментов обоих агентов
из терминала и Canvas обоих проектов. Один факт отправки запроса или
появление события вызова инструмента не считается успешным результатом.

Сценарии общей памяти и правил поддерживают `ACCEPT_AGENTS=qwen` либо
`ACCEPT_AGENTS=codex` для продолжения приёмки по одному агенту. По умолчанию
проверяются оба. Частичный запуск фиксировать отдельно: он не закрывает
матрицу до успешной проверки второго агента.

## Доступ, сеть и повторная установка

Проверить активацию и регистрацию через HTTP, включая срок и одноразовость,
параллельную подачу TOTP, сохранение лимита ошибок после перезапуска,
продление только при действиях пользователя, истечение и восстановление.
Отдельно проверить на настоящем Canvas: отзыв браузера закрывает его
соединение, но уже запущенная задача агента завершается.

Сетевая приёмка включает недоступность соседнего проекта, секретов VM,
метаданных облака и неразрешённых внутренних адресов. Во время остановки
mihomo новые исходящие подключения должны отказывать; восстановление
службы обязательно и при ошибке проверки.

Сетевой сценарий можно направить на эти же два проекта. Он также добавляет
контрольный файл и пакет `hello` для проверки сохранности после переустановки.

```bash
ACCEPT_PROJECT_A="$PROJECT_A" ACCEPT_PROJECT_B="$PROJECT_B" bash tests/accept_sandbox.sh before
# Повторная установка проверяемого релиза.
ACCEPT_PROJECT_A="$PROJECT_A" ACCEPT_PROJECT_B="$PROJECT_B" bash tests/accept_sandbox.sh after
```

До повторной установки сохранить контрольные значения рабочих файлов,
пакетов, истории, индексов, памяти, сессий и секретов в закрытом каталоге VM.
В протокол записывать только результат сравнения. Проверить:

- повтор тем же релизом;
- отказ на неверной конфигурации без изменения действующего состояния;
- повтор после исправления конфигурации;
- применение допустимого изменения управляемой конфигурации;
- сохранение всех контрольных данных и доступность инструментов.

Имеющиеся проверки сохранности графа и памяти дополняют эту сверку:

```bash
python3 tests/accept_project_recovery.py "$PROJECT_A" ./install.sh
python3 tests/accept_project_memory.py "$PROJECT_A" "$PROJECT_B" ./install.sh
python3 tests/accept_release_recovery.py "$PROJECT_A" "$PROJECT_B" ./install.sh
```

## Итоговый протокол

После изменений и живой приёмки выполнить полный набор `unittest` и
проверки Python, shell, Nginx и systemd на целевой VM. При проверке типов
сравнивать результат с исходным релизом, отдельно отмечая прежние замечания.
В отдельном окружении проверок нужны зависимости установленных модулей
(включая Graphiti/FalkorDB), официальный Python-пакет `mcp`, Playwright
и Pyright. Наличие Playwright само по себе не обеспечивает запуск всего набора.

В задаче 15 зафиксировать SHA, версию Ubuntu, среду, команды, коды завершения,
подтверждения каждого критерия и ограничения. Указать очистку временных
данных и итоговое состояние служб. Непройденные проверки не заменять
результатами предыдущих задач. Сливать ветку после полного выполнения
приёмки и независимого ревью.
