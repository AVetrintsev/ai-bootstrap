# Подключение Canvas

## Закреплённый контракт

Canvas 1.39.0 поставляется готовой сборкой npm; SHA-256 архива записан в `release.env`. Совместимые Agent Server, SDK и Tools закреплены на 1.62.0 согласно [defaults.json](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/config/defaults.json). Исходники Canvas не изменяются и не пересобираются.

В этой версии нет отдельного публичного API регистрации нескольких локальных backend из внешнего портала. Интеграция использует проверенный контракт реестра самой закреплённой сборки: [storage.ts](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/src/api/backend-registry/storage.ts) и [url-selection.ts](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/src/api/backend-registry/url-selection.ts). Это зависимость от версии, а не обещание совместимости с будущими версиями.

Защищённая страница `/canvas/open/gh-ID` проверяет готовность сервера и подготовленного разговора. Затем она добавляет в `openhands-backends` запись с отдельным ID и адресом `/agent/gh-ID`, выбирает её через `sessionStorage` и открывает разговор с параметром `backend=gh-ID`. Записи других проектов сохраняются. Этот параметр закрепляет проект за вкладкой. Флаг `openhands-onboarded` отражает выполненную платформой настройку Qwen. Реальный ключ сервера в HTML и хранилище браузера не передаётся.

Agent Server настраивается через штатные `/api/settings`, `/api/agent-profiles` и `/api/conversations`: создаётся профиль Custom ACP с командой `/usr/local/bin/qwen --acp`, выбирается разрешённая модель шлюза и создаётся разговор в `/workspace/repo` с `worktree: false`. Идентификатор разговора сохраняется вместе с ключом подключения; повторная подготовка использует прежний ID. Последующие пользовательские изменения профиля сохраняются.

При обновлении версии обязательно повторить браузерную приёмку на чистом хранилище браузера и в двух вкладках разных проектов. Проверить реестр, выбор backend в URL, профиль ACP, рабочую папку, вызов инструмента, HTTP и WebSocket. Обновлять номер и хеш сборки без этой проверки нельзя.

## Службы и границы доступа

- `ai-bootstrap-agent.service` — пользовательская служба песочницы; запускает Agent Server через существующий rootless-контейнер. История и настройки сохраняются на его диске.
- `ai-bootstrap-canvas-relay@PROJECT.socket` — Unix-сокет `0660 root:ai-portal`. Транспорт запускается от системного пользователя соответствующего проекта и соединяется только с Agent Server внутри его контейнера.
- `ai-bootstrap-canvas.service` — раздаёт готовые файлы Canvas и передаёт запросы из `/agent/PROJECT/` в фиксированный сокет проекта. Cookie портала в контейнер не передаётся. Адрес назначения не задаётся запросом браузера.
- Nginx проверяет сессию перед каждым обращением. Служба Canvas повторяет проверку и отслеживает отзыв/истечение во время потоковых соединений. Фоновые запросы срок сессии не продлевают.
- Нажатие клавиши или указателя в Canvas отправляет запрос активности не чаще раза в минуту. Он продлевает сессию и обновляет cookie; сервер требует совпадения Origin. Таймеры, HTTP-опрос и сообщения агента этого не делают.
- Повтор подготовки сохраняет работающий сервер, если версия и код запуска не изменились. При изменении поколения запуска или неудачной проверке готовности служба перезапускается; настройки и история находятся на постоянном диске проекта.

Для диагностики доступны `journalctl -u 'ai-bootstrap-projects@*.service'` и журнал пользовательской `ai-bootstrap-agent.service`. Не публикуйте файлы `/var/lib/ai-canvas/connections/*.json`: они содержат ключи серверов. После ошибки подготовки используйте повтор подключения в портале; удаление проекта остаётся отдельным действием с подтверждением.
