# Аудит использования OpenHands в ai-bootstrap

Дата: 16 ноября 2026 года. Основная база: `a5ce684333988195c934a1e9ebc9f04f9511f9eb` (`main`, PR #20).

## Вывод

Подозрение подтверждается частично. Мы используем OpenHands как готовый интерфейс, сервер разговоров и ACP-клиент, а исполнительные агентные циклы оставили Codex и Qwen. Это предусмотренный OpenHands режим работы, а не обход его архитектуры. Но **поверх готового стека мы написали собственную платформу эксплуатации и собственный адаптер Codex**. Именно последний — самый убедительный кандидат на сокращение собственного кода.

Неверно считать всю обвязку дублированием. Требования держать ChatGPT/GitHub/LLM credentials вне песочниц, выдавать доступ только своему репозиторию, отзывать браузерные потоки, сохранять постоянные контейнеры и публиковать общую память только после подтверждения владельца не исчезают при установке OpenHands. Готовая функция с похожим названием не обязательно сохраняет эти свойства.

Рекомендация: сохранить Canvas/Agent Server и границы платформы; проверить замену **переводчика Codex app-server → ACP** готовым `codex-acp` на доверенной стороне. Не начинать с удаления портала, шлюза или памяти. Для параллельной разработки отдельно использовать штатные worktree OpenHands после снятия наших ограничений рабочего каталога. Перевод всех заданий на native OpenHands Agent — отдельная смена исполнительного движка и пути авторизации/вызовов модели, а не простое удаление дублирования. SDK 1.62.0 имеет и собственный subscription transport: обязательный переход на платный API из такой смены не следует.

## Область и достоверность

- Изучены `lib/`, установщик, закреплённые версии, эксплуатационная документация, задачи 09/10 и исследования оркестрации. Непубликуемый `.scratch/ai-platform/spec.md` использован как локальный контекст; выводы о действующем контракте также опираются на отслеживаемые задачи и `docs/`.
- Закреплено в репозитории: Canvas **1.39.0**, Agent Server/SDK/Tools **1.62.0**, Codex **0.166.0**, Qwen Code **0.27.2**. Это версии из [release.env](../../release.env), а не доказательство версий каждого установленного Python/npm-пакета.
- Первичные источники и различия версий вынесены в [upstream-research.md](upstream-research.md). Возможность upstream отделена от её фактического использования у нас.
- Read-only осмотр целевой Linux VM подтвердил службы Canvas, проектных Codex/исполнителей, модельного шлюза, Graphiti и общей памяти. Службы с socket activation могут быть `inactive`, пока нет клиента; это само по себе не сбой.
- На VM также установлено расширение из отдельного коммита **`ebab82f`**, которого нет в проверенной `main`: загрузчик импортирует `agent_options`, а endpoint обращается к `_conversation._ensure_agent_ready`. Этот слой рассмотрен отдельно, без включения чужого коммита в ветку аудита.
- Доступ к root-only конфигурации и контейнерным пакетам не получен: `sudo -n` требует интерактивной аутентификации. Сквозные агентные тесты, нагрузочный benchmark и пробная миграция не проводились. Действующая платформа не изменялась. Все оценки сроков — инженерные диапазоны, не измеренный результат прототипа.

## Что действительно установлено и используется

```text
Браузер
  → Nginx + наш портал/сессия
  → готовый Canvas + наш proxy/реестр backend
  → OpenHands Agent Server внутри постоянного контейнера проекта
      ├─ Custom ACP → Qwen Code → наш шлюз → модель по API
      └─ Custom ACP → наш Unix-клиент → наш мост на хосте
                                            → Codex app-server + ChatGPT auth
                                            → exec-server в контейнере проекта

Codex и Qwen → Serena / CodeGraphContext / Graphiti MCP
```

[canvas-agent.py](../../lib/canvas-agent.py) создаёт настоящие OpenHands agent profiles через `/api/agent-profiles`, настройки через `/api/settings`, разговоры через `/api/conversations`; история OpenHands сохраняется в `OH_PERSISTENCE_DIR`. Собственной замены UI чата или хранилища событий OpenHands мы не написали. Хранение native Codex thread и событий Canvas — два уровня разных протоколов, а не две независимые реализации одного agent loop.

В обоих профилях выбран `agent_kind: acp`. SDK прямо отделяет этот режим от native Agent: внешняя программа владеет LLM и инструментами. Установка `openhands-tools` не означает, что Codex/Qwen используют эти tools. Конденсация контекста и native tools OpenHands не подключаются к ACPAgent как к обычному Agent; управление контекстом остаётся внешнему движку. MCP и prompt-контекст/skills при этом поддерживаются и в ACP-режиме. См. pinned [ACPAgent](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py).

## Где мы теряем возможности

1. **Урезанный Codex-контракт.** В [codex_service.py](../../lib/codex_service.py) зафиксирован небольшой перечень RPC и событий; неподдержанные методы отклоняются, дополнительные клиентские MCP запрещены. Новые upstream capabilities приходится вручную переводить. Приёмка должна учитывать usage, интерактивные запросы и события, а не только текст и shell.
2. **Нет изоляции одновременных изменений внутри проекта.** Два заранее созданных разговора Codex/Qwen используют одну директорию. `worktree:false` само по себе не сериализует задания. Внешние субагенты и scheduler тоже не получат изоляцию от одного переключателя: [codex-project.py](../../lib/codex-project.py) устанавливает `multi_agent=false`, мост и executor закрепляют cwd, индексы рассчитаны на `/workspace/repo`.
3. **Нельзя считать все кнопки Canvas возможностями внешнего агента.** Native `/plan` создаёт отдельного OpenHands Agent с LLM/tools/condenser; это не режим Codex по подписке. Нужны отдельная совместимая настройка LLM и проверка расхода. Передаваемые нашим мостом ACP `plan`-уведомления также нельзя считать доказанно отображаемым планом без проверки получателя; подробности в upstream-исследовании.
4. **Часть функций явно не развёрнута.** `OH_ENABLE_VSCODE=false`, `autotitle:false`, автоматизации исключены в [README](../../README.md) и контракте интеграции. Это не доказательство необходимости самописной замены. В частности, существующие файлы исследования оркестрации ещё не являются реализованным scheduler.
5. **Цена обновления скрыта в связности.** Browser storage contract, DOM `data-testid`, private SDK handshake, версии CLI/ACP и две конфигурации MCP связаны одновременно. Число удалённых строк не отражает выигрыш: главная экономия — меньше контрактов, которые приходится заново проверять на каждом обновлении.

## Почему готовый Codex-адаптер нельзя просто включить в контейнере

Разделение авторизации и исполнения было явным критерием [задачи 10](../ai-platform/issues/10-codex-subscription.md), а не случайной сложностью. Сейчас app-server и credentials находятся на хосте; `exec-server` запускается внутри rootless-контейнера с `include_local=false`. Клиент контейнера не получает полный app-server API.

Стандартный provider OpenHands поддерживает Codex subscription/file credentials. Это доказывает, что **для ACP не нужно автоматически отказываться от подписки**. Однако непосредственный запуск авторизованного адаптера там же, где сейчас находится Agent Server, не сохраняет нашу границу секретов.

Предпочтительный кандидат: готовый `codex-acp` на доверенном хосте + тот же remote executor + тонкий фильтр политики между недоверенным ACP-клиентом и адаптером. Совместимость закреплённых `codex-acp`, Codex 0.166.0 и remote environments пока не доказана запуском. Понадобятся проверка `CODEX_PATH`/управляемой конфигурации, запрет локального исполнения, разделение сессий проектов и оплаты, управляемые MCP и правила. Фильтр не должен снова превратиться в полный переводчик событий.

Миграция истории тоже не сводится к смене команды: нужно проверить соответствие OpenHands conversation ID, ACP session ID и Codex thread ID, каталогов состояния и allowed-session списка. Если бесшовное возобновление не получится, безопасный промежуточный вариант — новые разговоры на новом адаптере, старые продолжают использовать прежний профиль до завершения. Нужен явный план возврата; исходные данные не удаляются.

## Три варианта сокращения

| Вариант | Результат | Полная предварительная оценка | Цена/ограничения |
| --- | --- | --- | --- |
| **A. Сохранить продукт, сократить адаптеры** | Canvas/Agent Server + Codex/Qwen ACP; готовый Codex adapter на host; сохранены platform policy, память и контейнеры | **10–20 человеко-дней**, включая прототип 2–4 дня | Минимум изменений поведения. Срок зависит от совместимости адаптера с remote executor и историей. Большинство инфраструктурного кода останется обоснованно. |
| **B. Перейти на native OpenHands Agent** | Один основной agent loop и настройки через OpenHands; native tools, context management, delegation/worktree по потребности | **15–30 человеко-дней** | Меняется поведение агентов и путь авторизации. Native subscription есть, но перенос нашей host-auth схемы и доступность моделей/квот нужно проверить. API budget нужен выбранным API-профилям и вспомогательным моделям. CLI, история и MCP требуют миграции; изоляция и owner approval всё равно нужны. |
| **C. Упростить сам продукт до стандартного single-user OpenHands** | Убрать часть своего портала/provisioning/policy; принять модель готового развёртывания | **5–10 дней** только при заранее согласованном сокращении требований; **20–40+ дней**, если сохранять нынешние гарантии | Дешёвая версия перестаёт быть функционально равной платформой. Требует отдельно определить fate постоянных контейнеров, хостовых credentials, квот, browser revocation, памяти и CLI. |

Оценки не являются предложением внедрить B/C. В них не включены сроки upstream review, неопределённый перенос большого архива истории и ограничения подписки/API. В денежных единицах трудозатраты равны диапазону дней × дневная ставка команды; ставки и объём использования неизвестны, поэтому рублёвую сумму этот аудит не выдумывает.

Для B сначала выбирается способ доступа к каждой модели. SDK имеет `LLM.subscription_login` и собственный OpenAI OAuth/Responses transport ([auth source](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/llm/auth/openai.py), [subscription tests](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/tests/sdk/llm/test_subscription_mode.py)). Это отдельная реализация, а не автоматическое использование нынешнего trusted app-server; на нашей VM она не проверялась. Для API-профилей расходы считаются как входные/выходные токены × тарифы моделей, включая вспомогательные вызовы. Для subscription-профилей нужно проверить доступные модели и лимиты. Graphiti/embeddings остаются отдельным API-расходом, если память сохранена. Для A подписка не обязана исчезать; расходы Qwen API и памяти остаются. Точного сокращения RAM/CPU не обещаем: производительность не сравнивалась, а замена переводчика не удаляет Codex, MCP или Agent Server.

Общая оценка в этой таблице шире узких upstream-экспериментов из сопроводительного исследования: она включает перенос CLI/истории, платформенные границы, установку, восстановление и сопутствующие индексы. Разница диапазонов не является измеренной скоростью разработки.

## Рекомендуемая последовательность и критерии решения

1. **2–4 дня: проверить готовый Codex ACP на отдельном тестовом проекте.** Доказать host auth → container exec, `include_local=false`, запрет чужих сессий/cwd/MCP и отсутствие исполнения при отказе executor. Без этого менять production-профиль нельзя.
2. **Если совместимость подтверждена — заменить протокольную часть.** Проверить subscription/API separation без автоматического платного fallback, общий auth-lock, resume, модель/effort, изображения, tools/MCP, отмену, ошибки и завершение сессий. Проверить одновременно терминал и Canvas. Сохранить старый профиль для возврата до завершения переноса истории.
3. **Отдельно убрать хрупкие Canvas-зависимости через поддерживаемый контракт.** Effort-selector нужен до появления эквивалентного upstream UI; private handshake желательно заменить публичным endpoint/инициализацией. Простое обновление Canvas 1.39 → 1.40 эти проблемы не решает по проверенным исходникам.
4. **Перед scheduler/parallel agents включить worktree в согласованной модели исполнения.** Проверить два одновременных разговора одного проекта, соответствие Git branch/cwd, индексы, правила/память, возобновление и удаление только своего worktree. Не строить второй менеджер worktree без проверки штатного.
5. **Остальные компоненты сокращать только по отдельной потребности.** Отказ от графа памяти, общей approval-процедуры или постоянных контейнеров — продуктовые решения. Их нельзя прятать под названием «удалить дублирование».

Имеющиеся Linux-сценарии дают основу: `test_codex.py`, `test_canvas.py`, `accept_codex_isolation.py`, `accept_codex_mcp.py`, `accept_canvas.py`, `accept_canvas_options.py`, `accept_canvas_revocation.py`, приёмки tools/memory/rules. Для миграции их нужно направить на новый transport и добавить проверки границ, которые изменятся. В рамках этого аудита эти сценарии не запускались и их успех не заявляется.
