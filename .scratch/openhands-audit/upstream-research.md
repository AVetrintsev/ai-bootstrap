## Вывод

Использование Canvas с Custom ACP — штатный сценарий OpenHands. Установка `openhands-sdk` и `openhands-tools` не означает, что Codex/Qwen работают как встроенный OpenHands Agent. Собственные интерфейс, история и профили в основном **уже делегированы upstream**. Основное функциональное пересечение — протокольный перевод Codex app-server → ACP, потому что upstream уже использует готовый такой адаптер. Основные отличия платформы — доверенный контроль учётных данных, привязка к проекту, ограничения файлов/исполнителя/моделей, владелец и подтверждение общей памяти. Эти ограничения нельзя убрать под видом удаления дублей. [Границы Canvas](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/docs/architecture.md), [контракт ACPAgent](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py#L1), [готовый Codex ACP](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/README.md).

**Нельзя делать вывод «ACP не поддерживает skills/MCP/memory/images»**: SDK 1.62.0 поддерживает эти пути с оговорками ниже. **Нельзя делать и обратный вывод «все функции SDK автоматически действуют в ACP»**: native tools, condenser и native approval loop не управляют внешним агентом.

## ACP: реальные границы, а не общие предположения

1. **Native tools и condenser не подключаются к ACP.** `ACPAgent.init_state` бросает `NotImplementedError` при `tools` или `condenser`. Внешний агент владеет инструментами и context management. Поэтому наличие OpenHands browser/terminal/task tools в установленном wheel не делает их доступными Qwen/Codex. Для использования этих инструментов нужен native OpenHands Agent либо отдельный MCP/иной bridge. **Уверенность высокая.** [Код](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py#L2475).

2. **MCP поддерживается.** `mcp_config` преобразуется в ACP servers (stdio, HTTP/SSE по capabilities), передаётся при session/new и session/load; ACP subprocess сам устанавливает соединения. Это позволяет переиспользовать настройки OpenHands, но наш Codex bridge отклоняет клиентские `mcpServers` намеренно, поскольку список исполняемых команд задаётся доверенным `codex-project.py`. Перенос MCP UI допустим только с сохранением этой политики или её явным пересмотром. **Высокая.** [Conversion](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py#L780), [session launch](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py#L3379).

3. **Skills поддерживаются двумя путями.** При `acp_skill_sourcing=native` CLI читает свою конфигурацию и repository; OpenHands не инжектирует managed skills. `openhands_managed` добавляет server-discovered user/org/public/marketplace skills. Переданные клиентом launch skills сохраняются в обоих режимах. Project skills намеренно не дублируются: CLI должен читать AGENTS.md сам. Managed skills материализуются в файлы и prompt catalog. В ai-bootstrap pip-запуск Agent Server не задаёт override, поэтому действует default `native`, если его не меняет внешняя среда. **Высокая для контракта; средняя для полного runtime env без отдельной проверки.** [Config](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-agent-server/openhands/agent_server/config.py#L465), [materialization](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_skills.py).

4. **Постоянная память тоже есть и совместима с ACP.** `AgentContext.load_memory` по умолчанию false; при включении читает user/project `.openhands/memory/MEMORY.md`, общий бюджет 6000 символов, daily logs не загружает автоматически. Это файловая агентная память. Она не заменяет семантический поиск Graphiti/FalkorDB, внешнюю БД проекта, owner-only publish и неизменное одобряемое содержание общей памяти. **Высокая.** [AgentContext](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/context/agent_context.py#L143), [memory loader](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/context/memory.py).

5. **Инструкции можно передавать штатно**, включая system_message_suffix, но ACP превращает prompt context в добавку к сообщению, а не гарантированно в native developer/system channel внешнего engine. Наши owner rules вставляются в Codex `developerInstructions` и Qwen `--append-system-prompt`; store недоступен агенту для записи. Совпадение текста инструкции не означает совпадения authority и контроля изменения. **Высокая.** [ACP context rendering](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/context/agent_context.py#L496), [local shared-rules](../../docs/shared-rules.md).

6. **Approval UI native Agent не защищает ACP.** Bridge автоматически выбирает первый permission option; elicitation declines. Встроенный Codex preset задаёт `agent-full-access`. Контроль безопасности ACP должен находиться в engine/исполнителе/платформе, а не подразумеваться из наличия Verification settings. **Высокая.** [request_permission](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py#L1784), [preset](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/settings/acp_providers.py#L440).

7. **Параллельность имеет несколько разных смыслов.** Несколько conversations/worktrees штатны. Native SDK `TaskToolSet` поддерживает подагентов, их persistence/resume и параллельные calls; этот tool нельзя вставить в ACPAgent из-за пункта 1. Готовый codex-acp умеет собственные native ACP subagent sessions после bilateral negotiation, иначе fallback tool-call. Это не доказывает end-to-end UI support именно Canvas 1.39.0. В локальном `codex-project.py` `multi_agent=false` задан явно: отсутствие подагентов здесь также продуктовая политика. **Высокая для слоёв, непроверено для полного UI сценария.** [SDK subagents](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/examples/01_standalone_sdk/25_agent_delegation.py), [adapter contract](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/README.md#subagent-sessions).

## Два конкретных UI-ограничения

### Reasoning selector — расширение пробела, не повтор готового UI

Проверены `chat-input-model.tsx`, `use-chat-input-model-state.ts`, `agent-server-adapter.ts`, `agent-server-conversation-service.api.ts` и ручная ACP-форма `agent-settings.tsx` в 1.39.0. UI переносит models/current model и вызывает model switch, но не переносит available/current efforts и не вызывает effort switch. В ACP-форме сохранение включает model/command/args; generic `SchemaField` используется для native tool concurrency, не для всех ACP schema fields. Поэтому наличие `acp_effort` в SDK schema **не создаёт автоматически selector в Canvas**. Проверенный diff 1.39.0 → 1.40.0 такой selector тоже не добавляет. **Уверенность высокая для изученного UI, это чтение положительного data flow, не только пустой поиск.** [Selector](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/src/components/features/chat/components/chat-input-model.tsx), [сохранение ACP](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/src/routes/agent-settings.tsx#L291), [SchemaField только native](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/src/routes/agent-settings.tsx#L1272), [release diff](https://github.com/OpenHands/OpenHands/compare/v1.39.0...v1.40.0).

`lib/canvas-reasoning.js` — временная DOM-интеграция поверх штатного API, с ценой сопровождения selector/testid, poll 4 с и lazy initialization. Правильное направление сокращения — upstream UI contribution/upgrade после появления функции. Просто удалить этот файл сейчас значит убрать доступный пользователю выбор effort. Отдельный незамёрженный `canvas-agent-options.py` (`ebab82f`) использует private `_ensure_agent_ready` для холодного Custom ACP; это дополнительная version-coupled заплатка, а не публичная функция upstream. Перевод на known Codex preset может дать штатный pre-session discovery, но лишь после проверки доверенной topology.

### ACP Plan notification не равен видимому плану Canvas

`_OpenHandsACPBridge.session_update` в SDK 1.62.0 явно обрабатывает text/thought/usage/tool start/tool progress. Остальное попадает в debug-only `else`. Отдельного преобразования ACP `plan` notification здесь нет. Значит корректная отправка `sessionUpdate:"plan"` нашим Codex bridge сама по себе не доказывает, что Canvas сохранит/покажет план. Это подтверждённый разрыв преобразования; фактическую видимость следует проверять Linux/browser сценарием. Встроенный Canvas planner — другой механизм, описанный выше. **Высокая уверенность по transform, runtime-эффект ещё не воспроизводился этим исследованием.** [Весь dispatch](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py#L1573).

## Sandbox, auth, secrets и gateway

Штатный Agent Server поддерживает local/docker runtime и выбор per-conversation runtime, memory/CPU/PID limits, persistence/retention. Canvas сам не является isolation layer. Это функционально пересекается с запуском песочниц, но upstream per-conversation Docker lifecycle и наш per-project rootless Podman/systemd lifecycle — разные схемы владения. Сокращение systemd/Podman слоя потребует переноса томов, сети, uid, credentials, остановки/восстановления и тестов изоляции. **Высокая.** [Runtime config](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-agent-server/openhands/agent_server/config.py#L404).

Штатное self-hosting использует backend API key; в public mode пользователь вводит его в Canvas. Workspace cookie применяется только к workspace serving, остальные API требуют header. Это не наш owner login, отзыв сессий во время WebSocket, продление только по действию пользователя и скрытый реальный backend key. Следовательно защищённый relay нельзя признать дублем обычного reverse proxy без потери этих свойств. **Высокая.** [SELF_HOSTING](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/docs/SELF_HOSTING.md#L48), [auth cookie boundary](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-agent-server/openhands/agent_server/auth_router.py#L1).

SDK умеет encrypted secret storage/key rotation, profile scopes, Codex credential bindings и передачу secrets внешнему процессу. Его модель предполагает, что этот процесс получает соответствующие credentials (env или материализованный auth file). Поддержка `OPENAI_BASE_URL`/`CODEX_CONFIG` означает возможность **пользоваться** gateway, а не наличие эквивалента нашим per-project allowed models/daily quota/max tokens/request validation и скрытым provider keys. **Высокая.** [Secret key config](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-agent-server/openhands/agent_server/config.py#L358), [credential binding](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-agent-server/openhands/agent_server/credential_binding.py), [Codex proxy env](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/agent/acp_agent.py#L529).

## Готовый Codex adapter на host: реальная альтернатива, но ещё не готовая замена

Готовый `@agentclientprotocol/codex-acp@2.2.2` уже переводит ACP в Codex App Server и обратно, включая model/effort, auth, text/images, plans, reasoning, tools, cancellation, session load/fork. Это **реальное функциональное дублирование переводящей части `codex_service.py`**, а не только похожий интерфейс. Адаптер позволяет `CODEX_PATH`, `CODEX_CONFIG`, `MODEL_PROVIDER`, наследует process env и запускает app-server как subprocess. Следовательно не нужно выбирать только между «credentials внутри sandbox» и «отказаться от подписки». [README](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/README.md), [spawn](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/src/CodexJsonRpcConnection.ts#L34), [entry/config](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/src/index.ts#L98).

**Кандидат с сохранением архитектуры:** оставить per-project host service, закрытый Unix ACP endpoint, trusted `CODEX_HOME`, `environments.toml` с `default=project`/`include_local=false`, executor socket и owner auth service; внутри host service запускать готовый adapter с закреплённым `CODEX_PATH=/opt/ai-codex/bin/codex`. Внешний policy proxy валидирует/переписывает ACP requests до adapter. App-server thread/start не задаёт environment override; текущая платформа тоже полагается на default environment. Поэтому совместимость с remote executor **правдоподобна**, но не подтверждена исполнением. **Уверенность средняя, не объявлять drop-in.** [newSession](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/src/CodexAcpClient.ts#L791), [локальная конфигурация](../../lib/codex-project.py).

Что policy proxy всё равно должен сохранить:

- Разрешённые cwd и session IDs только проекта; запрет arbitrary MCP commands/additional directories/config, auth/logout/provider switching и расширений, меняющих доверенную конфигурацию.
- Жёсткий выбор subscription/API без автоматического перехода, проверку account type и остановку после изменения режима оплаты.
- Owner rules как доверенные инструкции при создании **и** resume; клиентский `_meta` не должен заменять их. Готовый adapter принимает custom instructions из AIR metadata при newSession, что требует отдельного фильтра.
- Проверки remote executor до/после задания, отказ без local fallback, sanitization ошибок и неразглашение credentials.
- Session/load и существующую историю при смене adapter; наблюдаемость, отмену, поведение при crash/restart и concurrent auth refresh.

Эти пункты следуют из нынешнего `lib/codex_service.py` и расширенной поверхности готового адаптера: у него есть authentication, logout, session list/fork и config options. Замена должна **сократить event/protocol mapping, сохранив authority enforcement**. [Adapter routes](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/src/index.ts#L149), [custom instructions](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/src/CodexAcpClient.ts#L791).

Отдельная цена: dependency адаптера — `@openai/codex:^0.160.1`, а проект закрепляет Codex 0.166.0. `CODEX_PATH` позволяет избежать незаметной смены binary, но совместимость версий, adapter host-side filesystem assumptions и bootstrap hooks всё равно нужно проверить. Нельзя обещать полное сохранение поведения по одним env options. [Package](https://github.com/agentclientprotocol/codex-acp/blob/202e66e63343ec4f5a5e35ab590251d813d129ca/package.json).

## Уточнение: native OpenHands тоже умеет ChatGPT subscription

В SDK 1.62.0 есть **не только Codex ACP subscription**, но и native LLM subscription mode: `LLM.auth_type="subscription"`, `subscription_vendor="openai"`, OAuth browser/device-code login и `OpenAISubscriptionAuth.create_llm()`. Он формирует LLM к Codex Responses endpoint и восстанавливается из сохранённого LLM profile. Canvas 1.39.0 также содержит отдельные subscription service и auth card в LLM settings. Поэтому переход на native Agent **не означает обязательную утрату подписки или обязательную оплату всех запросов по API**. **Уверенность высокая по наличию реализации; работа конкретного аккаунта и текущего deployment не проверена.** [Native auth](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/llm/auth/openai.py#L761), [profile restoration](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/llm/llm.py#L3384), [Canvas subscription service](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/src/api/llm-subscription-service.ts), [Canvas auth card](https://github.com/OpenHands/OpenHands/blob/5aed815f5384c48bccacf1e40a8619653d488ad0/src/components/features/settings/llm-settings/openai-subscription-auth-card.tsx).

Это другой auth/LLM transport, не текущий host Codex app-server. Он хранит/обновляет OAuth credentials на стороне выполняющего LLM процесса и имеет собственные особенности Responses: поток, `store:false`, отключённые несовместимые параметры. Сохранение host-only credentials при native Agent внутри нынешнего контейнера потребует новой схемы trusted execution/gateway; простая смена профиля не переносит текущий security contract. Не делается юридических выводов о допустимости любого варианта использования: установлен только технический факт поддержки upstream. API-бюджет следует считать для выбранных API-профилей и вспомогательных моделей, а не автоматически для всего native сценария. [Request construction](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/openhands-sdk/openhands/sdk/llm/auth/openai.py#L803), [subscription regression contract](https://github.com/OpenHands/software-agent-sdk/blob/504a88cab0fb48ee5226238ad7b8f1d865fa84a8/tests/sdk/llm/test_subscription_mode.py).

## Что даёт обновление и сколько стоит переход

Canvas 1.40.0 исправляет tied history page boundaries, delayed echo/drafts, home model choice при отключённых profiles, выбор реальной default branch и пояснения Codex subscription auth. Оно **не** добавляет новый reasoning selector и не меняет перечисленные архитектурные границы; SDK latest уже совпадает с pin. Обновление ради удаления всех локальных adapters не обосновано. [Release 1.40.0](https://github.com/OpenHands/OpenHands/releases/tag/v1.40.0), [полный diff](https://github.com/OpenHands/OpenHands/compare/v1.39.0...v1.40.0).

Оценки ниже — предварительный инженерный диапазон для одного разработчика, не коммерческая смета; включают обязательную Linux-приёмку и зависят от результатов прототипа.

| Сценарий | Что реально сокращается | Оценка / цена |
|---|---|---|
| Сохранить topology, использовать доступные Canvas функции | Не создавать вторые history/profile/settings/diff UI; worktrees включать только после согласования cwd policy; reasoning fix отправить upstream | 1–3 дня на узкий integration cleanup; перенос worktrees отдельно 2–5 дней из-за fixed cwd и lifecycle. Большую часть platform services это не убирает |
| Готовый codex-acp на host за тонким policy proxy | Перевод app-server events, images, models/effort, cancellation/history; сохраняются auth/control/executor services | 2–4 дня доказательный прототип на VM + 4–10 дней реализация/регрессии при успешном результате. Возможны adapter fixes для remote environment, не обещать экономию заранее |
| Native OpenHands Agent вместо Codex/Qwen engine | Собственные CLI adapters; открываются native tools/condenser/TaskToolSet/planner | 1–3 недели и отдельная оценка поведения/стоимости моделей. Меняется harness и auth/transport; native ChatGPT subscription существует, но текущая изоляция credentials и настройки автоматически не переносятся. Graphiti, owner rules, gateway и isolation сами собой не исчезают |
| Штатный Docker runtime вместо per-project Podman/systemd | Часть lifecycle/resource management | 2–4 недели миграции и проверок данных/credentials/network/isolation; это изменение платформенной архитектуры, а не мелкий cleanup |

## Ограничения исследования

- Не запускались тесты, сборки или приложение на Windows/WSL. Linux/runtime проверку ведёт основной агент отдельно; выводы о коде не выдаются за end-to-end приёмку.
- Просмотрены versioned trees и исполняемые ветви перечисленных областей. Отсутствие поисковой выдачи не использовалось как доказательство отсутствия функции.
- Не заявляется отсутствие любой возможной third-party integration, enterprise capability или новой unreleased ветки. Сравнение newer ограничено подтверждённым release 1.40.0 и latest SDK 1.62.0 на дату исследования.
- Миграция готового Codex adapter на host — проверяемая гипотеза с конкретными extension points. Её ещё нужно доказать на установленном Codex 0.166.0, remote exec-server и текущих trust boundaries.
- Слой `canvas-agent-options.py` из `ebab82f` отмечен отдельно от main; он не включён в оценку уже принятого main-кода.
