# Оркестрация агентов: практики и варианты для ai-bootstrap

Дата исследования: 2026-11-16. Это исследование и предложения для обсуждения, **не согласованная архитектура и не спецификация реализации**. Внешние сведения проверены по первичным источникам; рекомендации обозначены отдельно. Вопросы grilling ещё могут изменить границы решения.

## Подтверждено владельцем в первом раунде grilling

- Порядок: разбор запроса → grilling → план → исполнение; существенные новые неизвестные возвращают процесс к вопросам.
- Подключать **только готовых CLI-агентов**. Прямые model API как интерфейс исполнителя или планировщика в текущий замысел не входят. Сведения ниже о gateways и общих runtimes оставлены как сравнение альтернатив.
- Цель: **снизить стоимость без потери качества**. Какую стоимость оптимизировать и как измерять сохранение качества, ещё уточняем.

**Следствие для рекомендации:** оркестратор вызывает CLI через поддерживаемый программный интерфейс (ACP, app-server, headless JSON и т. п.). Планирование и review также выполняет выбранный CLI-агент. Провайдер модели, способ авторизации и тарификация остаются свойствами конкретного CLI; CLI-интерфейс сам по себе не означает работу по подписке.

**Предложение по экономии:** сравнивать полную стоимость успешного результата, включая grilling, планирование, review и повторы. Уменьшение использования фиксированной подписки может сберечь лимит, не меняя платёж. Сохранение качества следует подтверждать на типичных задачах; гарантировать его для любого будущего запроса исследование не позволяет.

## Что уже есть в практике

Сценарий «принять задачу → уточнить → спланировать → назначить исполнителей → проверить → исправить» соответствует нескольким известным паттернам. Anthropic разделяет заранее заданные workflows и системы, в которых модель сама выбирает дальнейшие действия; рекомендует начинать с минимальной сложности и учитывать цену дополнительных шагов. Статья 2024 года теперь предупреждает, что инструментарий изменился, поэтому здесь она используется как источник паттернов, а контракты инструментов сверяются отдельно. [Building effective agents](https://www.anthropic.com/research/building-effective-agents).

| Паттерн | Подтверждённый смысл | Возможное применение здесь — рекомендация |
| --- | --- | --- |
| Routing | Классификация запроса и передача подходящему обработчику | Отличать вопрос, исследование, изменение кода, диагностику и эксплуатационную операцию |
| Orchestrator–workers | Центральная модель динамически делит работу и объединяет результаты работников | Выдавать ограниченные подзадачи агентам с подходящими возможностями |
| Evaluator–optimizer | Генератор получает оценку и исправляет результат в цикле | Отдельный review по критериям приёмки с ограниченным числом исправлений |

Определения в таблице взяты из [Anthropic](https://www.anthropic.com/research/building-effective-agents). Это композиционные приёмы, а не требование заводить несколько агентов для каждого сообщения.

**Рекомендация:** единая точка входа может принимать все задачи, сохраняя короткий путь для простых запросов. Оркестратор должен иметь возможность выбрать одного исполнителя. Для сложной задачи роли планировщика, grilling и reviewer стоит разделить по контексту и полномочиям, но разные роли не обязательно требуют разных провайдеров.

**Рекомендация:** grilling сделать отдельным этапом с явным результатом: принятые ограничения, открытые вопросы, допущения и критерии приёмки. Вопрос человеку нужен там, где ответ изменяет решение; повторное согласование уже разрешённого действия не должно становиться обязательным ритуалом.

## Две разные задачи: выбирать модель и запускать агента

**Вариант A — общий agent runtime с несколькими model providers.** PydanticAI предоставляет агенту модель, инструменты, типизированный результат и ограничения использования. В одном runtime можно задавать модель при запуске; `UsageLimits` ограничивает запросы и вызовы инструментов. Учёт стоимости имеет ограничения и не заменяет ограничения расходов у провайдера. [PydanticAI Agents](https://pydantic.dev/docs/ai/core-concepts/agent/).

LiteLLM унифицирует параметры model API, но поддерживаемые параметры различаются: неподдерживаемый OpenAI-параметр по умолчанию вызывает ошибку, а `drop_params` может его отбросить. [LiteLLM Input Params](https://docs.litellm.ai/docs/completion/input). OpenRouter предоставляет нормализованный интерфейс reasoning с ограничениями конкретной модели. [OpenRouter Reasoning Tokens](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

**Вывод:** общий model API удобен для собственного планировщика или evaluator, но сам по себе не воспроизводит файловые инструменты, управление контекстом, сессии и разрешения чужого coding agent. Это разные уровни интеграции.

**Вариант B — запуск существующих agent runtimes.** Claude Agent SDK, например, запускает Claude Code binary и предоставляет его инструменты, permissions, sessions и hooks; Client SDK для модельного API — другой интерфейс. Codex app-server и Qwen headless также имеют собственные контракты сессий и исполнения. [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview), [Codex app-server](https://learn.chatgpt.com/docs/app-server), [Qwen 0.27.2 headless](https://github.com/QwenLM/qwen-code/blob/v0.27.2/docs/users/features/headless.md).

| Вариант | Что контролирует платформа — архитектурный вывод | Основной компромисс — оценка |
| --- | --- | --- |
| Общий runtime + model API | Agent loop, инструменты, память, permissions, выбор провайдера | Проще единый контракт, больше собственной ответственности за качество coding harness |
| Адаптеры Codex / Claude / Qwen | Задания и lifecycle над уже готовыми агентами | Сохраняются особенности агентов; нужно нормализовать разные события и ограничения |
| Смешанный | Общие планировщик/evaluator плюс специализированные coding workers | Подходит текущей базе, но требует явно разделить состояние workflow и сессии worker |

**Уточнённая рекомендация для ai-bootstrap после первого раунда:** выбрать вариант адаптеров готовых CLI, переиспользуя Codex и Qwen. Сервис workflow хранит состояние и вызывает CLI, а интеллектуальные роли планировщика/evaluator исполняются через эти же адаптеры. Сначала проверить, достаточно ли одного сервиса и двух адаптеров; новый model gateway для этого не требуется. Конкретный движок workflow ещё не выбран.

## Реальные контракты запуска

### Codex

Upstream app-server использует handshake `initialize` / `initialized`, затем `thread/start` либо `thread/resume`, `turn/start`, поток событий и `turn/completed`. Поддерживаемые модели и reasoning предлагается получать через `model/list`: значения зависят от аккаунта и клиента. [Codex app-server](https://learn.chatgpt.com/docs/app-server).

В ai-bootstrap закреплён Codex 0.166.0. Платформенный `codex` — ограниченный клиент, поддерживающий диалог, `codex exec '…'` и `codex --acp`; произвольные native CLI flags не обещаны. Авторизация находится на доверенной стороне, исполнение — в rootless-контейнере, доступная рабочая папка ограничена `/workspace/repo`. Публичный сокет не предоставляет полный app-server RPC. [Документация платформы](../../docs/codex.md), [закреплённые версии](../../release.env), [реализация моста](../../lib/codex_service.py).

**Следствие для проектирования:** upstream `model/list` не означает, что метод уже доступен оркестратору через нынешний ACP-мост. Нужен отдельный аудит разрешённых операций и адаптер на соответствующей стороне границы доверия. Не следует запускать произвольный native Codex внутри контейнера с перенесёнными туда ChatGPT credentials.

### Claude Code / Agent SDK

Официальный неинтерактивный CLI запускается как `claude -p "…" --output-format json`; доступны `stream-json`, resume и SDK для Python/TypeScript с callbacks разрешений. JSON содержит результат и метаданные сессии; для streaming документирован отдельный контракт событий. [Claude Code programmatic usage](https://code.claude.com/docs/en/headless).

Официальная документация Agent SDK рекомендует API key authentication и отдельно ограничивает предложение third-party продуктами входа через claude.ai / его rate limits без предварительного согласования Anthropic. Это не утверждение о запрете личного интерактивного CLI; для добавления SDK в платформу нужно выбрать допустимый способ авторизации. [Claude Agent SDK overview](https://code.claude.com/docs/en/agent-sdk/overview).

**Рекомендация:** рассматривать Claude как новый адаптер, а не считать его уже развёрнутым. Фиксировать версию binary/SDK и проверять возможности при подключении.

### Qwen Code 0.27.2

В закреплённой версии документированы `qwen -p "…" --output-format json`, `stream-json` и `--resume SESSION_ID`. Лимиты headless включают `--max-session-turns`, `--max-wall-time`, `--max-tool-calls`. Существенная оговорка: лимит tool calls учитывает верхний уровень, а не внутренние действия subagents; в ACP/serve путь этих wall-time/tool-call настроек не применяется. Persistent retry для 429/529 — явный opt-in и способен ждать неограниченно. [Qwen 0.27.2 headless](https://github.com/QwenLM/qwen-code/blob/v0.27.2/docs/users/features/headless.md).

Платформа уже запускает Qwen через `/usr/local/bin/qwen --acp`, а Canvas создаёт разговор с `worktree: false` в `/workspace/repo`. [Canvas в ai-bootstrap](../../docs/canvas.md).

**Следствие:** нельзя приписывать текущему ACP-пути бюджетные гарантии headless CLI. Нужны ограничения и отмена снаружи worker, а также проверка фактического завершения процесса и дочерних действий.

### Авторизация и оплата — отдельные свойства

В текущей платформе Codex ChatGPT и API — отдельные профили. Исчерпание подписки не включает платный API автоматически; изменение профиля требует нового разговора. [Codex в ai-bootstrap](../../docs/codex.md).

**Рекомендация:** хранить `auth_profile` и `billing_profile` независимо от имени модели. Не считать наличие CLI-подписки доступом к произвольному model API. Fallback допустим только внутри заранее разрешённых провайдеров, способов оплаты и границ передачи данных.

## ACP, A2A и MCP: разные границы

ACP описывает client↔agent связь: согласование capabilities, создание/загрузку сессии, prompt, updates, permissions и cancel. `session/load` зависит от объявленной поддержки. На момент исследования официальная документация различает v1 и draft v2. [ACP v1 overview](https://agentclientprotocol.com/protocol/v1/overview).

A2A предназначен для сотрудничества агентов, MCP — для подключения инструментов и ресурсов; спецификация A2A прямо рассматривает их как дополняющие протоколы. [A2A and MCP](https://a2a-protocol.org/latest/topics/a2a-and-mcp/).

**Вывод для платформы:** ACP подходит для UI/адаптеров локальных coding workers; A2A можно рассмотреть при появлении независимо размещённых агентов. Serena, CodeGraphContext и Graphiti через MCP дают возможности и контекст, но подключение этих инструментов само по себе не задаёт маршрутизацию, бюджет, очередь задач или правила merge.

**Рекомендация:** не вводить ACP, A2A и новый model gateway одновременно ради унификации. Достаточен внутренний контракт worker с адаптацией фактически поддерживаемых возможностей; внешний протокол добавлять по конкретной интеграционной потребности.

## Сохранение состояния и ожидание человека

LangGraph использует checkpointer и `thread_id` для сохранения состояния. `interrupt()` позволяет ждать внешний ответ и продолжать через `Command(resume=…)`. При продолжении узел запускается с начала: код до interrupt выполняется повторно. [LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts).

LangGraph отдельно предупреждает о побочных эффектах при retry: ключ идемпотентности должен восстанавливаться из уже сохранённого состояния, а отсутствие подтверждения не доказывает, что действие не произошло. При неизвестном исходе нужно сверять состояние внешней системы. [LangGraph Fault tolerance](https://docs.langchain.com/oss/python/langgraph/fault-tolerance).

Temporal предлагает durable workflow, продолжающийся после сбоя и длительного ожидания человека; в официальном AI-разделе есть интеграции с agent frameworks. [Temporal Durable AI](https://docs.temporal.io/ai). Для Activities по умолчанию предусмотрены retries; Workflow Execution не имеет аналогичной retry policy по умолчанию. [Temporal Retry Policies](https://docs.temporal.io/encyclopedia/retry-policies).

| Кандидат | Основание для выбора — оценка, требующая прототипа |
| --- | --- |
| LangGraph | Удобно явно описать ветвления, роли, состояние диалога и HITL в Python |
| Temporal | Полезен, если главное — длительные задания, внешние workers, восстановление и операционный контроль |
| Собственный небольшой state machine | Можно ограничить зависимости, но самостоятельно придётся доказать recovery, дедупликацию и работу очереди |

**Рекомендация:** выбрать одного владельца состояния задания. Не начинать с вложенных LangGraph и Temporal без доказанной необходимости. Сессия Codex/Qwen остаётся состоянием конкретного worker; она не заменяет состояние всего задания.

**Предлагаемый контракт состояния:** идентификаторы задания и попытки, проект, запрос, версия плана, ответы grilling, текущая стадия, зависимости, worker/session IDs, модель/effort, выделенный и израсходованный бюджет, разрешения, commit SHA, артефакты проверок, последнее подтверждённое внешнее действие и причина остановки.

**Предлагаемая машина состояний:**

```text
received → classified → clarifying → planned → executing → verifying → reviewing
                         ↑              ↑          │             │
                    human reply         └── bounded repair ──────┘
reviewing → integrating → completed
любая активная стадия → waiting_input / paused / failed / cancelled
```

Схема — рекомендация. `waiting_input` не должен занимать живой LLM-запрос; повторное сообщение человека должно адресоваться конкретному заданию и версии вопроса. Закрытие вкладки не должно неявно определять судьбу задания.

## Выбор модели и reasoning

Универсальное правило «всем high» не следует из API-контрактов. Codex публикует supported/default reasoning efforts через `model/list`. OpenRouter нормализует `effort` и token budget, однако модели поддерживают разные режимы; reasoning может расходовать общий бюджет выходных токенов. [Codex app-server](https://learn.chatgpt.com/docs/app-server), [OpenRouter reasoning](https://openrouter.ai/docs/guides/best-practices/reasoning-tokens).

**Рекомендация:** выбирать по capabilities: coding harness, tools, structured output, context window, поддержка reasoning, resume/cancel, изоляция, разрешённый provider и способ оплаты. Для неизвестной возможности возвращать `unsupported`, а не молча отбрасывать существенный параметр.

**Стартовая гипотеза для оценки, не обещание качества:**

- Классификация и извлечение структуры: дешёвая быстрая модель с проверяемой схемой результата.
- Планирование и неоднозначная диагностика: более сильная модель; effort повышать при измеримой необходимости.
- Изменение кода: coding agent, которому доступны нужные инструменты и среда проверки.
- Review: отдельный контекст с diff и критериями приёмки; иной провайдер — эксперимент, а не гарантия независимости.
- Неудача: сначала определить, вызвана ли она моделью, инструментом, средой или неверной задачей; только затем выбирать повтор, уточнение либо смену исполнителя.

## Бюджет, retries и цикл разработки

Следующие пункты — рекомендации для спецификации:

1. **Бюджет всего задания.** Ограничить расходы, токены, время, число работников, глубину делегирования и число исправлений. Выдавать дочернему запуску резерв из общего лимита; учитывать внутренние subagents и повторные API-запросы.
2. **Управляемые остановки.** Различать timeout, нехватку бюджета, отсутствие авторизации, исчерпание подписки, отказ исполнителя, пользовательскую отмену и неопределённый результат внешнего действия.
3. **Повторы по типу сбоя.** Временный API-сбой допускает ограниченный backoff; невалидный результат — ограниченное исправление; отказ прав — изменение условий. Timeout после `push`/создания PR/merge требует сверки серверного результата, а не слепого повтора.
4. **Изоляция записи.** Независимому исполнителю кода выдавать отдельную рабочую копию и ветку. До поддержки этого режима разрешать один writer на проект. Интеграцию результатов делать отдельным шагом, а не параллельным редактированием общей папки.
5. **Проверки как артефакты.** Сохранять команду, целевую среду, exit code и commit SHA; reviewer должен знать, какой именно код проверен. Новые изменения после проверки могут потребовать её повторения.
6. **Review и merge.** Reviewer возвращает конкретные замечания и решение по критериям приёмки. Оркестратор считает работу завершённой после требуемого результата на сервере, а не после фразы модели «готово».
7. **Наблюдаемость.** Сохранять краткую причину маршрута, версии агентов, события lifecycle, стоимость/usage с указанием полноты учёта и ссылки на артефакты. Для пользователя показывать стадии, блокировку и следующий шаг.

В этом репозитории отдельная task-ветка, промежуточные commit/push, завершение через PR merge и проверки только на целевой Linux-машине уже являются обязательными правилами. Запуск тестов на Windows или WSL запрещён. [AGENTS.md](../../AGENTS.md).

## Как проверить, что оркестратор приносит пользу

**Предлагаемый эксперимент:** сравнить один хорошо настроенный coding agent с маршрутизируемым процессом на одинаковом наборе реальных задач. Сначала выполнить маршрутизацию в режиме наблюдения, затем включить ограниченный пилот; не менять сразу все проекты.

Набор должен включать короткий вопрос, небольшую правку, баг с воспроизведением, несколько независимых изменений, исследование, неоднозначную задачу с grilling и операцию с внешним побочным эффектом.

Измерять успешность приёмки, полную стоимость и время, число вмешательств пользователя, лишние уточнения, ошибки выбора worker, повторные действия после сбоя и соответствие проверенному commit. Проверить также отмену, перезапуск процесса, ожидание ответа, сбой провайдера и исчерпание бюджета.

**Критерий выбора — предложение:** усложнение должно улучшить качество, предсказуемость либо стоимость на этих задачах. Если routing не обгоняет baseline, сохранить один агент как основной путь и применять дополнительные роли только к доказанным случаям.

## Что остаётся решить

- Какие типы задач входят в первую версию и где заканчиваются полномочия оркестратора?
- Нужен ли grilling для каждого изменения или только при существенной неопределённости?
- Какие способы авторизации/оплаты CLI разрешены и каков бюджет на задачу и сутки?
- Как задаются правила автоматического merge и эксплуатации?
- Достаточно ли последовательных coding workers или нужна параллельная запись в независимых рабочих копиях?
- Что должно переживать перезапуск: только задача, диалог с человеком или также активный worker turn?

Реализация не выполнялась. Исследование не включает запуск агентов с платным inference, проверку их поведения на целевой VM или тесты проекта. Соответствие адаптеров закреплённым версиям и recovery-гарантии предстоит подтвердить отдельным ограниченным прототипом после определения требований.
